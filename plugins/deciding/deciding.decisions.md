# deciding
- D1: この判断リストは，何もない状態から，decidingスキルを作り，自作スキルをまとめたリポジトリから配布する．
    - 「何もない状態から」がないと，既存のファイルを前提にした判断として読まれうる．
- D2: このスキルの目的は，AIの作業をユーザーが精査し（D3），ユーザーの指示をAIが精査すること（D4）．
    - 目的に線引きと指示の精査があれば，ルールにない場面でも，AIは作業そのものをユーザーに頼まず，指示の不整合を探すことを基準に判断できる．
- D3: AIの作業をユーザーが精査するとは，ユーザーに求めるのは判断だけで，作業はAIがするということ．成果物に入る選択のうち，ユーザーが別の答えを選びうるものは，ユーザーがカードで見て決めたものか，`RUN`後の一覧（D40）で見られる形でAIに任せたものだけにする．要件も実装上の判断も対象にする．
    - 成果物を見てから気づいた選択は，直すのも，なぜそうなったかを追うのも高くつく．
- D4: ユーザーの指示をAIが精査するとは，AIが指示に従うだけの役ではなく，議論の相手として自分の推奨と反論を出し，判断の食い違いや理由が成り立たなくなった判断を起票するということ．
    - AIが賛成しかしないと，ユーザーは自分の案の弱点を知らないまま`OK`する．
- D5: 想定する使い方は，ユーザーが十分と思う抽象度まで決めた時点で`RUN`すること．`RUN`の結果を見て判断を足す使い方も妨げないが，手順はそれに合わせない．
    - 細部まで人が決めると，自分で実装するのとほとんど変わらず，AIを使う意味が薄れる．
    - 小刻みに`RUN`する使い方に合わせると，`RUN`のたびに確認を挟む規則が要る．
- D6: このスキルは，1つの判断にかかる手間を下げる．
- D7: 語は，判断として定める．判断の文面では定義した語だけを使い，同じ概念を別の語で呼ばない．
- D8: 「AI」は，スキルに従って動くものを指す．「アシスタント」とは呼ばない．
    - 「アシスタント」には指示を受けて手伝う役という意味が入り，D4と逆を向く．
- D9: 「実行環境」は，作業時点で存在するコードベース，外部の情報，AIが動く環境を指す．
- D10: 「成果物」は，コード，コメント，ドキュメント，コミットメッセージ，PRの説明など，作業の結果として残るものすべてを指す．判断リスト（改善の対象を除く）と，セッション中の会話は含まない．
- D11: AIがユーザーに判断を求める依頼を「カード」と呼び，スキルの基本の比喩とする．質問のほか，説明や記録済みの判断の見直しの提案も含む．カードは，問いを見出しに，推奨・理由・代替を欄として持つ．`OK`になったカードの推奨が判断になる．カードは種類に分けない．AIが起票してからユーザーが返答するまでを「ラウンド」，`OK`になっていないカードを`OPEN`と呼ぶ．
    - 「1枚に1つ」や「カードに書いた内容に`OK`が及ぶ」のような規則が，比喩から自然に読める．
    - どのカードも，ユーザーに答えを求めている点は同じ．
    - カードは，質問のほかに質問への答えや説明，反論，改善の勧め，見直しの提案も運ぶので，「質問」では実態より狭い．
- D12: AIがカードを作って出すことを「起票」と呼ぶ．
    - 「出す」は，`SHOW`や`RUN`の一覧のようにカード以外の出力にも使う．別の語にすれば区別できる．
- D13: ユーザーが返答以外に書いたことを「投げ込み」と呼ぶ．まとまっていない考えのままでよい．
    - まとまっていなくてよいと書かないと，考えがまとまってから話すものと思われやすい．
- D14: 投げ込みは，ユーザーの意見の1つとして扱う．AIはそれを前提にせず，ゼロベースで推奨を作る．ユーザーの案を推奨にしないときは代替に置き，採らない理由を書く．
    - 整えて返すだけだと，ユーザーの案が前提になり，最初の`DEAL`の案がそのまま推奨として`OK`される．
    - 意図はユーザーにしか分からず，整合性はAIのほうがよく見られる．AIがゼロベースで推奨を出し，ユーザーが承認する形なら，両方が活きる．
- D15: 構成・命名・形式に標準的なものがあれば，それを推奨にする．ユーザーの案が標準と違うときは，標準から外れる意図があるかを問う．
    - AIの強みは標準を知っていることで，ユーザーの恣意的な選択を前提にすると，その強みが使われない．
    - 標準から外れた選択は，あとで読む人や他のツールに対して説明が要る．
- D16: AIは，成果物に影響し，ユーザーが別の答えを選びうる選択を，すべて候補にする．出すか迷う選択も候補にする．
- D17: AIが指示されなくても満たすことは，SKILL.mdにも判断リストにも書かず，候補からも外す．
    - 不要な制約を書くと，そのぶん読む量が増え，本当に必要な制約が埋もれる．
- D18: AIは，記録済みの判断や，セッション中に`OK`になった判断と同じこと，またはそこから導けることを候補にしない．
    - 判断リストの重複の多くは，AIが起票したカードから入る．
- D19: 投げ込みやコメントに含まれる事項は候補にし，起票するかどうかはほかの候補と同じ順位で決める．
    - 投げ込みと1対1で起票すると，投げ込みの数だけカードが増え，枚数の上限と両立しない．
    - 上位に入らなかった事項も，`RUN`後の一覧で確かめられる．
- D20: 候補の順位は，他の判断の前提になるものを先にし，次に，成果物の中で変わる範囲が大きいものを先にする．起票もこの順に並べる．
    - 前提になる判断が決まれば下位のカードの切り方が変わるので，先に決めるほど無駄なカードが減る．
    - 依存と影響範囲なら，AIの感覚ではなく成果物から確かめられる．
- D21: AIは，候補をすべて洗い出してから順位を付け，1ラウンドに上位5枚だけを起票する．
    - 枚数が多いと，本質的でないカードに埋もれ，噛み合わないときにそのセッションの中で立て直せない．
    - 枠が限られていれば，AIは何を出すかを吟味せざるをえない．
- D22: 毎ラウンド，確定した判断，投げ込み，コメントから候補を作り直し，上位から起票する．前のラウンドの`OPEN`や`SKIP`のカードは持ち越さず，同じ事項でも順位に入ったときだけ起票する．
    - カードを持ち越すと，確定した前提ができる前の切り方が残り，`SKIP`したカードが居座る．
- D23: 最初のラウンドでは，作業の目的（何を，どの状態から作るか）を問うカードを起票する．
    - どの状態から作るかが記録にないと，`RUN`のとき，その時点の実行環境を前提にして読みかねない．
- D24: カードは，1枚で1つのことだけを問う．推奨の中に，片方だけに賛成・反対できる部分が2つ以上あれば，分ける．
    - 一部にだけ賛成・反対できないカードは，コメントしにくい．
- D25: 依存する下位のカードは，上位が`OK`になった次のラウンドで，その内容に合わせて起票する．下位があることは，上位のカードの理由に書く．
    - 同時に起票すると，上位が推奨以外の内容で`OK`になったとき，下位の`OK`を取り消すことになる．
- D26: ラウンドの出力では，ユーザーに見せる情報は，質問への答えや説明も含め，すべてカードに書く．関係するカードがなければ新しいカードにする．カードの外には，今回`OK`になった判断の一覧と，返答のお願いのような進行のための文だけを書く．
    - カードの外に書いたものは，`OK`の対象かどうかがはっきりせず，ユーザーが確認しないまま記録に残る経路になる．
- D27: 推奨・理由・代替という欄の構成は，どのカードでも緩めない．依頼も，推奨にAIが勧める答え，理由にその根拠，代替にほかの答えを書く．
    - 形式が1つなら，読み方も1つで済む（D28）．
    - 欄を緩めると，推奨のないカードが生まれ，AIが議論の相手として自分の案を出さなくなる．
- D28: AIに当てがない質問では，推奨に「当てがない」と書き，代替に考えられる答えを並べる．
    - 形を変えなければ，見る形式は1つのまま．
- D29: 1枚の長さには，上限ではなく目安を設ける．推奨は3文，理由は3項目，ラベルなしの補い（D30）は2項目まで．
    - 1つの判断にかかる手間に最も効くのは読む量で，数字のない「短く」では長くなりがち．
    - 上限にすると，分けられない判断の理由を削ることになり，削った理由は`OK`されないまま抜け落ちる（D35）．
- D30: カードでは，推奨・理由・代替だけをラベル付きの欄として書く．それ以外の補いは，ラベルなしの箇条書きで自由に書く．ラベル付きの欄は，内容が1つならラベルと同じ行に，複数ならラベルの下の入れ子の箇条書きに書く．
    - 決まった欄はラベルで探せ，それ以外を自由にすれば，書式を増やさずに書ける．
- D31: カードには，`C1`，`C2`のような番号を，ラウンドごとに1から振り直して付ける．番号は，返答の宛先や依存関係のように，同じラウンドの中でカードを指すためだけに使う．
    - 番号がないと，ユーザーは問いを書き写して返答することになる．
    - 役目を同じラウンドの中に限れば，新しく起票するか更新かを決める必要がなくなる（D22）．
    - 判断のID（D52）と頭文字を変えるのは，記録済みの判断を変えるカード（D57）で，カードの番号と対象のIDが並ぶため．`#1`の形はObsidianでタグになる．
- D32: カードの理由に，他の判断と矛盾しないことを示すだけの項目を書かない．
    - 矛盾しないことは判断の根拠にならず，カードに書いた理由はそのまま記録に残る（D35）．
- D33: カードで記録済みの判断に触れるときは，どの欄でも，判断に要る内容をカードの中に書く．IDは添えてもよいが，IDだけでは指さない．
    - ユーザーが読むのはカードだけで，判断リストはAIが読む前提で書かれている．IDだけでは，判断の前提がカードに出てこない．
- D34: 返答は，`OK`（推奨で確定する），`SKIP`（そのラウンドでは判断しない．返答のないカードも同じに扱う），コメント（それ以外のすべて．`NG`や「いいよ」も含む）の3つだけにする．
    - 返答の種類が少なければ，ユーザーが選ぶ手間も，ルールの量も減る．
- D35: `OK`は，カードに書いた推奨と理由の両方に及ぶ．理由に異論があれば，コメントで修正する．記録する理由は，カードに書いたものから変えない．
    - 記録のときにAIが理由を書き足すと，`OK`されていない理由になる．
- D36: セッション中に`OK`になった判断は，ユーザーがその内容を挙げて変えたいとコメントすれば，`OPEN`に戻して起票し直す．それに依存して`OK`になった判断も`OK`を取り消し，下位のカード（D25）として扱う．
    - 決まりがないと，コメントだけで判断が変わるか，まったく変えられないかのどちらかになる．
- D37: 食い違いや，実行環境の変化などで理由が成り立たなくなった判断に気づいたら，候補にする．セッション中に`OK`になった判断どうしなら，D36の方法で`OPEN`に戻し，食い違いを解いた推奨で起票し直す．記録済みの判断が実行環境や他の記録済みの判断と食い違う，または理由が成り立たなくなったなら，そのカードでは記録済みの判断を変えず，先に判断リストの改善（D56）を勧める．
    - 食い違う判断を両方`OK`のまま`RUN`すると，どちらに従うかをAIが決めることになる．
    - 食い違いだけを拾うと，矛盾はないが理由が古くなった判断が残り続ける．
- D38: 指示の語を，`DEAL`（起票する），`SAVE`（判断リストに記録する．D41），`SHOW`（セッション中に`OK`になった判断を，判断リストの書き方でチャットに出す．ファイルには書かない），`RUN`（成果物を作る．D39），`COMPRESS`（指定した判断リストを対象に，圧縮（D48）を目的とする判断リストの改善（D56）を始める）の5つにする．英大文字の語は，それだけで書かれたときに限って指示とみなす．「記録して」のように明示的に頼む文も，同じ指示として受ける．
    - 返答（D34）と同じ形になり，ユーザーが打つ語が揃う．それだけで書かれたときに限るのは，「テストをrunする」のようなふつうの文で，誤って成果物を作りはじめないため．
    - `DEAL`はカードを配ること，`SHOW`は手札を見せることを指し，カードの比喩に合う．`SHOW`があれば，ファイルを書けない環境でも判断リストをコピーでき，書き出す前に記録される形を確かめられる．
- D39: ファイルを指定しない`RUN`は，セッション中に`OK`になった判断に従って成果物を作り，先に`SAVE`はしない．ファイルを指定した`RUN`は，そのファイルの判断にも従う．`OPEN`のカードが残っていても確かめずに進め，それらはAIの自由な判断に任せる．
    - `RUN`の前に`OPEN`を確かめ直すと，`SKIP`でAIに任せた意味がなくなる．
- D40: `RUN`で成果物を作ったあと，AIが自由に判断した選択のうち，ユーザーが別の答えを選びうるものを，チャットに一覧で出す．
    - 一覧があれば，ユーザーは任せた選択を見て，必要なものだけ次のカードにできる（D3）．
- D41: `SAVE`と指示されたときに，そのセッションで`OK`になった判断をすべて，新しい判断リストのファイルに書く．既存のファイルには追記しない．同じセッションで再び`SAVE`したときは，そのセッションのファイルを書き直す．ファイル名の末尾（D49）より前は，ユーザーが指定できる．
    - 記録のタイミングをユーザーが決められ，ラウンドのたびに書き込まずに済む．
    - 判断している段階では，既存の判断リストへの追記か更新かを決められない．既存のファイルに入れたいときは，判断リストの改善（D56）として行う．
- D42: `SAVE`の前には，セッション中に`OK`になった判断に見直しのフロー（D43）を当てる．`RUN`の前には，`OK`になった判断どうしや記録済みの判断との食い違いだけを確かめる．どちらも，食い違いは途中で止めたことで生じたものに限り，候補が見つかれば実行せず，上位5件まで起票する．同じ指示がもう一度あれば，見直さずに実行する．
    - 矛盾とまではいえない指摘が大量に出ると，`SAVE`のたびに本筋でない判断を迫られる．上位だけなら，ユーザーは目を通して，重要でないと思えば無視して進められる．
    - 見直す対象はまだ記録していないセッション中の判断なので，見つかったものはその場のカードで直せ，判断リストの改善を別に始めずに済む．
    - 食い違いは気づいたら候補にするが（D37），気づかないまま確定すると，整合しない判断が記録に残る．
- D43: 見直しのフロー（候補を洗い出し（D46），順位を付けて上位5件を起票し，最後に整える（D47））は，SKILL.mdの1つの見出しの下に手順として書く．
    - 見出しで区切られていれば，その部分だけを別のエージェントに渡せる．
- D44: `SAVE`前の見直しと`COMPRESS`の候補探しは，判断リストと見直しのフローだけを渡した別のエージェントにさせる．別のエージェントを使えない環境では，AI自身が行う．
    - 判断を作った文脈のまま確かめると，自分の推奨を前提に読んでしまい，依存や理由の一貫性の確認が甘くなる．
    - 別のセッションへ持っていかなくても，文脈を持たない状態で確かめられる．
- D45: 見直しをさせる別のエージェントには，呼び出し元と同じモデルを使わせ，時間がかかることは受け入れる．
    - 環境によっては，別のエージェントに軽いモデルが既定で割り当てられ，見直しが甘くなる．文脈を切り離した意味がなくなる．
    - 見直しは`SAVE`と`COMPRESS`のときだけなので，時間がかかってもラウンドの進みは遅くならない．
- D46: 見直しのフローでは，判断の内容が変わるものだけを候補にする．対象は，食い違い，消してAIの自由な判断に任せても成果物がおおむね同じになると見込める判断，定義がなくても読み違えない語を定める判断，判断を支えていない理由（不正確な理由や，その判断がなくても成り立つ一般論）．判断と理由は，書き直さず削除することを推奨にする．
    - 候補を内容の変わるものに絞れば，上位5件の枠が本当に判断の要るものに使われる．
    - 重複を消すだけでは，役目を終えた判断が残り続け，判断リストは膨らむ一方になる．
    - 理由の書き直しを候補にすると，見直しのたびに文面が増えうる．
- D47: 見直しのフローの最後に，内容を変えない整えを，カードにせずに行う．表記揺れを直し，分けられる判断を分け，他の判断から導ける判断や文を消す．
    - 内容を変えない書き換えはカードにしない（D57）ので，候補探しとは別の手順にしておかないと，カードの枠を使ってしまう．
- D48: 圧縮では，対象の判断リストに見直しのフローを当てる．
    - カードの規則は，規則ができる前に記録された判断や，すり抜けた判断には効かない．
- D49: 判断リストは，名前と置き場所の決まった1つのファイルではなく，ファイル形式として扱う．中身はMarkdownで，文字コードはUTF-8（BOMなし），改行はLF，ファイル名の末尾は`.decisions.md`にする．AIが判断リストを書くときも書き換えるときもLFにし，対象がCRLFならLFに直す．既定の置き場所は設けない．
    - 判断リストの改善では，対象の判断リストと改善作業の判断リストが並ぶ．
    - 末尾が決まっていれば，名前が何であっても形式が分かる．
    - Windowsの環境では，AIが改行や文字コードの違いで判断リストの更新に手間取りやすい．形式として決めておけば，どこに置かれても同じ規則が効く．
- D50: 判断リストには，名前の見出しの下に判断だけを並べる．ほかの見出しや，日時のような判断以外の情報は書かない．
