# deciding
- D1: この判断リストは，何もない状態から，decidingスキルを作り，自作スキルをまとめたリポジトリから配布する．
    - 「何もない状態から」がないと，既存のファイルを前提にした判断として読まれうる．
- D2: このスキルの本質は「ユーザーは決めるだけ，AIは作るだけ．AIは指示に従うだけの役ではなく，自分の推奨と反論を出す議論の相手になる」とし，SKILL.mdの冒頭に書く．
    - 本質が先頭にあれば，ルールにない場面でも，作業をユーザーに頼まず，指示の不整合を探すことを基準に判断できる．
    - AIが賛成しかしないと，ユーザーは自分の案の弱点を知らないまま`OK`する．
- D3: スキルが守る原則を，追跡（成果物に入る選択のうちユーザーが別の答えを選びうるものは，ユーザーがカードで決めたものか，`RUN`後の一覧で任せたと分かるものだけにする），独立（推奨はユーザーの案とは別に実行環境と標準から作る），忠実（記録に残るのはユーザーが見て`OK`した文面だけで，AIは記録に書き足さず，ユーザーが理解したかも確かめない）の3つにし，本質の下に番号付きで書く．ほかの規則はこの3つから導ける形にする．
    - 成果物を見てから気づいた選択は，直すのも，なぜそうなったかを追うのも高くつく．
    - 整えて返すだけだと，ユーザーの案が前提になり，最初の案がそのまま`OK`される．
    - 記録のときにAIが理由を書き足すと，`OK`されていない理由になる．
    - 規則が原則から導けるなら，規則の数を増やさずに場面を広げられる．
- D4: 想定する使い方は，ユーザーが十分と思う抽象度まで決めた時点で`RUN`し，残りをAIに任せて一覧で確かめること．小刻みに`RUN`する使い方に手順は合わせない．
    - 細部まで人が決めると，自分で実装するのとほとんど変わらない．
    - 小刻みな`RUN`に合わせると，`RUN`のたびに確認を挟む規則が要る．
- D5: 語は，判断として定める．判断の文面では定義した語だけを使い，同じ概念を別の語で呼ばない．
- D6: 「AI」は，スキルに従って動くものを指す．「アシスタント」とは呼ばない．
    - 「アシスタント」には指示を受けて手伝う役という意味が入り，D2と逆を向く．
- D7: 「実行環境」は，作業時点のコードベース，外部の情報，AIが動く環境を指す．
- D8: 「成果物」は，コード，コメント，ドキュメント，コミットメッセージ，PRの説明など，作業の結果として残るものすべてを指す．判断リスト（改善の対象を除く）とセッション中の会話は含まない．
- D9: AIがユーザーに判断を求める依頼を「カード」と呼び，スキルの基本の比喩とする．問いを見出しに，推奨・理由・代替を欄として持ち，種類に分けない．カードを作って出すことを「起票」，起票からユーザーの返答までを「ラウンド」，`OK`になっていないカードを`OPEN`と呼ぶ．
    - 「1枚に1つ」や「カードに書いた内容に`OK`が及ぶ」のような規則が，比喩から自然に読める．
    - カードは質問のほかに説明，反論，見直しの提案も運ぶので，「質問」では実態より狭い．
- D10: `OK`になったカードの推奨と理由を「判断」と呼ぶ．判断リストにあるものを記録済みの判断，今のセッションで`OK`になったものをセッションの判断と呼ぶ．判断にない選択をAIが決めたものを「任せた選択」と呼ぶ．
    - 「セッション中に`OK`になった判断」「AIが自由に判断した選択」を毎回書くと，規則が長くなる．
- D11: ユーザーが返答以外に書いたことを「投げ込み」と呼ぶ．まとまっていなくてよい．
    - まとまっていなくてよいと書かないと，考えがまとまってから話すものと思われやすい．
- D12: 指示の語を`DEAL`（起票する），`SAVE`（セッションの判断を判断リストに書く），`SHOW`（`SAVE`と同じ内容をファイルに書かずチャットに出す），`RUN`（成果物を作る），`COMPRESS`（指定した判断リストに見直しを当てて起票し，以後は判断リストの改善として進める）の5つにし，表で書く．英大文字の語は，それだけで書かれたときに限って指示とみなす．「記録して」のように明示的に頼む文も同じ指示として受ける．指示がなければ，判断が必要な場面でも自発的に起票しない．
    - 返答と同じ形になり，ユーザーが打つ語が揃う．それだけで書かれたときに限るのは，「テストをrunする」のようなふつうの文で誤って成果物を作りはじめないため．
    - `SHOW`があれば，ファイルを書けない環境でも判断リストをコピーでき，書き出す前に記録される形を確かめられる．
    - 表なら，指示の一覧と各節への入口が1か所で見える．
- D13: 指示の節の直下に，`DEAL`と`COMPRESS`から`SAVE`・`RUN`までの流れを1つの図で書く．
    - 流れが1か所にあれば，各節がどこで使われるかを探さずに読める．
- D14: セッションの中では，ユーザーが指定した判断リストだけを読む．指定のない判断リストを探して読まない．
    - 判断リストの改善では対象も判断リストで，見つけたファイルを従うべき判断として読んでしまう．
- D15: ラウンドは，返答を処理する，候補を洗い出す，推奨を作る，順位を付ける，出力する，の5手順として番号付きの小節に書く．`DEAL`のときも返答を受けるたびも，同じ手順で起票する．場面ごとの規則は，その場面が現れる手順の中に置く．
    - 手順が明示されていないと，場面の網羅をAIの読み取りに頼ることになり，抜けが出る．
    - 規則を手順に置けば，同じ規則を2か所に書かずに済む．
- D16: 返答は，`OK`（推奨と理由で確定する．条件や修正が付いていればコメント），`SKIP`（このラウンドでは判断しない．返答のないカードも同じ），コメント（それ以外すべて．`NG`も「いいよ」も含む）の3つだけにする．カード番号を添え，番号のない`OK`や`SKIP`だけの返答は全カードへの返答とみなす．
    - 返答の種類が少なければ，ユーザーが選ぶ手間も，ルールの量も減る．
    - 条件付きの`OK`を`OK`に含めると，カードに書いていない文面が判断になる．
- D17: `SKIP`とコメントのカードは捨て，その事項とコメントの内容は候補に戻す．ユーザーが内容を挙げてセッションの判断を変えたいと書けば，その判断と，それに依存する判断の`OK`を取り消し，候補に戻す．
    - カードを持ち越すと，確定した前提ができる前の切り方が残り，`SKIP`したカードが居座る．
    - 決まりがないと，コメントだけで判断が変わるか，まったく変えられないかのどちらかになる．
- D18: 成果物に影響し，ユーザーが別の答えを選びうる選択を，すべて候補にする．出すか迷うものも候補にする．要件も実装上の判断も対象にする．投げ込みとコメントの事項も候補にし，ユーザーの提案もユーザーが`OK`して確定する．
    - 投げ込みと1対1で起票すると，投げ込みの数だけカードが増え，枚数の上限と両立しない．
- D19: 指示されなくても満たすこと，判断と同じこと，判断から導けることは，候補から外す．ユーザーの提案がこれにあたるなら，どの判断から導けるかを理由に書いて反論する．
    - 判断リストの重複の多くは，AIが起票したカードから入る．
- D20: 判断どうしの食い違い，実行環境の変化などで理由が成り立たなくなった判断，上位の判断に依存する下位の事項を候補に加える．下位は上位が`OK`になった次のラウンドで出し，下位があることは上位の理由に書く．
    - 食い違いだけを拾うと，矛盾はないが理由が古くなった判断が残り続ける．
    - 上位と下位を同時に起票すると，上位が推奨以外の内容で`OK`になったとき，下位の`OK`を取り消すことになる．
- D21: 最初のラウンドでは，作業の目的（何を，どの状態から作るか）を必ず候補にする．
    - どの状態から作るかが記録にないと，`RUN`のときの実行環境を前提に読んでしまう．
- D22: 推奨は，候補ごとに，まず投げ込みとコメントを見ずに実行環境と標準から答えを作り，次にユーザーの案と比べ，勝つほうを推奨に，負けたほうを代替に置く．推奨がユーザーの案と同じなら，推奨の末尾に「（ユーザー案）」と記す．
    - 比べる順序を手順に書かないと，ユーザーの案を前提に推奨を作る．
    - 印があれば，なぞりが起きていることをユーザーとAIの両方が見られ，続けば気づける．
    - AIの強みは標準を知っていることで，ユーザーの案を前提にするとその強みが使われない．
- D23: 代替には，推奨が崩れたら次に推せる案を書く．検討していない案や形だけの案は書かない．理由には，推奨が代替に勝る根拠を書く．他の判断と矛盾しないことだけを示す項目は書かない．
    - 代替が形だけだと，理由も比較にならず，推奨の弱点がカードに出てこない．
    - 矛盾しないことは判断の根拠にならず，カードの理由はそのまま記録に残る．
- D24: AIに当てがなければ，推奨に「当てがない」と書き，代替に考えられる答えを並べる．判断に資料が要るなら，推奨は「この資料を渡す」，代替は「渡さず，AIが推測で進める」にする．
    - 欄を緩めると推奨のないカードが生まれ，AIが自分の案を出さなくなる．
- D25: セッションの判断どうしの食い違いは，解いた推奨で起票する．記録済みの判断が実行環境や他の記録済みの判断と食い違うなら，そのカードでは変えず，判断リストの改善を推奨にする．
    - 食い違う判断を両方`OK`のまま`RUN`すると，どちらに従うかをAIが決めることになる．
- D26: 候補の順位は，他の判断の前提になるものを先に，次に成果物の中で変わる範囲が大きいものを先にする．上位5枚だけをこの順に起票する．候補は毎ラウンド作り直し，順位に入ったときだけ再び起票する．
    - 前提になる判断が決まれば下位のカードの切り方が変わるので，先に決めるほど無駄なカードが減る．
    - 枚数が多いと本質的でないカードに埋もれ，噛み合わないときにそのセッションの中で立て直せない．
- D27: 出力は通常のテキストで，選択肢UIは使わない．書くのは，今回`OK`になった判断の一覧，カード，返答のお願いだけ．説明や質問への答えも関係するカードの補いに書き，関係するカードがなければ新しいカードにする．
    - カードの外に書いたものは，`OK`の対象かどうかがはっきりせず，ユーザーが確認しないまま記録に残る経路になる．
- D28: カードは1枚で1つのことだけを問う．推奨の中に，片方だけに賛成・反対できる部分が2つ以上あれば分ける．
    - 一部にだけ賛成・反対できないカードは，コメントしにくい．
- D29: カードの番号は`C1`，`C2`のようにラウンドごとに1から振り直し，同じラウンドの中でカードを指すためだけに使う．
    - 番号がないと，ユーザーは問いを書き写して返答することになる．
    - 役目を同じラウンドの中に限れば，新しく起票するか更新かを決める必要がなくなる．
    - 判断のIDと頭文字を変えるのは，判断リストの改善で番号とIDが並ぶため．
- D30: 推奨・理由・代替はどのカードでも欄として書き，内容が1つならラベルと同じ行に，複数ならラベルの下の入れ子に書く．それ以外の補いはラベルなしの箇条書きで書き，`OK`は補いには及ばない．
    - 決まった欄はラベルで探せ，それ以外を自由にすれば，書式を増やさずに書ける．
    - 補いに`OK`が及ばないと明記しないと，説明の文面が判断に混ざる．
- D31: 長さは目安とし，推奨3文，理由3項目，補い2項目．上限ではない．
    - 数字のない「短く」では長くなりがち．
    - 上限にすると，分けられない判断の理由を削ることになり，削った理由は`OK`されないまま抜け落ちる．
- D32: カードで記録済みの判断に触れるときは，判断に要る内容をカードの中に書く．IDは添えてもよいが，IDだけで指さない．
    - ユーザーが読むのはカードだけで，判断リストはAIが読む前提で書かれている．
- D33: 判断リストは，名前と置き場所の決まったファイルではなくファイル形式とし，Markdown，UTF-8（BOMなし），改行はLF，ファイル名の末尾は`.decisions.md`にする．書くときも書き換えるときもLFにし，対象がCRLFならLFに直す．
    - 判断リストの改善では，対象の判断リストと改善作業の判断リストが並ぶ．
    - Windowsの環境では，改行や文字コードの違いで判断リストの更新に手間取りやすい．
- D34: 判断リストは，AIが実行環境と合わせて読めば成果物を作れる指示として書く．何度実行しても記録済みの判断はいつも満たされるようにし，成果物そのものが毎回同じになることは求めない．実行環境の内容は書き写さないが，判断の中で言及してよい．記録にない選択は，`SKIP`したものも含め，任せた選択になる．
    - 記録にない選択はAIがその都度決めるので，成果物は毎回変わりうる．改修や計画立案では，判断が実行環境を前提にする．
- D35: 判断リストには，名前の見出しの下に判断だけを並べ，ほかの見出しや日時のような情報は書かない．他の判断の前提になるもの，影響範囲の大きいものの順に並べ，IDもその順に`D1`から振る．IDは判断リストの中の参照にだけ使い，書き換えるたびに並べ直して参照も直す．
    - 前提になる判断から読めば，`RUN`でも`COMPRESS`でも後ろの判断を正しく読める．
- D36: 各判断は，`OK`になった推奨を本文に，カードの理由をそのまま入れ子に書く．「理由:」のラベルは書かず，入れ子は理由だけにする．問いがないと意味が通らない場合だけ問いの語を補う．列挙を含む判断は，列挙を本文に書くか，項目ごとに別の判断に分ける．
    - 判断ごとにラベルの行が増えるぶん，読む量が増える．
- D37: 判断リストとSKILL.mdでは，指示されなくても満たすことは書かず，同じ説明を2か所に書かず，同じことを別の言い方で書かない．
    - 不要な制約を書くと読む量が増え，本当に必要な制約が埋もれる．SKILL.mdは起動のたびに全部読み込まれる．
- D38: `SAVE`は，セッションの判断を判断リストの書き方にして見直しを当て，候補が出れば書かずに起票する．見直しで起票した直後の`SAVE`は見直さずに書く．新しいファイルに書き，既存のファイルには追記しない．同じセッションの2回目以降はそのファイルを書き直す．ファイル名の末尾より前と置き場所は，ユーザーの指定がなければAIが決める．ファイルを書けない環境では`SHOW`と同じにチャットに出す．
    - 気づかないまま確定すると，整合しない判断が記録に残る．
    - 判断している段階では，既存の判断リストへの追記か更新かを決められない．
    - claude.aiのようにファイルを書けない環境でも，同じ指示で動く．
- D39: ファイルを指定しない`RUN`はセッションの判断に従い，ファイルを指定した`RUN`はその判断リストの判断にも従う．先に`SAVE`はしない．作る前に従う判断どうしの食い違いだけを確かめ，あれば作らずに起票し，その直後の`RUN`は確かめずに作る．`OPEN`のカードは確かめ直さず任せた選択にする．作る途中で判断を満たせないと分かったら，止めて起票する．
    - `RUN`の前に`OPEN`を確かめ直すと，`SKIP`で任せた意味がなくなる．
    - 満たせない判断を黙って曲げると，一覧にも記録にも残らない選択ができる．
- D40: `RUN`で成果物を作ったあと，任せた選択のうちユーザーが別の答えを選びうるものを，チャットに一覧で出す．成果物には書かない．
    - 一覧があれば，ユーザーは任せた選択を見て，必要なものだけ次のカードにできる．
- D41: このスキルを使っていること，判断リストがあること，判断がどう決まったか（判断リストやIDへの参照，スキル名，「合意に基づき」「ユーザーの判断で」のような書き方）は成果物に持ち込まない．判断の理由を成果物に残すときは，成果物の中だけで意味が通る文で書き，書くかどうかはふつうのコメントの書き方として判断する．このスキルや判断リストを扱うツールを作る作業と判断リストの改善では，スキルや判断リストのことを書いてよいが，IDや「〜で決めた」のような経緯は持ち込まない．
    - 判断リストは公開リポジトリに入るとは限らず，IDはファイルごとに振るので，別のファイルや書き換え後では別の判断を指す．
    - 理由を書くことまで禁じられていると読まれると，コードを読む人に必要な理由まで書かれなくなる．
- D42: スキルは，記録済みの判断を書き換える機能を持たない．判断リストの改善は，対象の判断リストを成果物とするふつうの作業とし，`RUN`で対象を書き換え，`SAVE`では改善作業の判断を別の判断リストに書く．
    - 更新のための仕組みを持たずに済み，改善の判断もほかの成果物と同じ流れで確定し，記録できる．
- D43: 対象の判断を変えるカードは，問いに元のIDと内容を1行で，推奨に変更後の文面ではなく何を含め何を含めないかを，理由に元の判断から何が変わるかを書く．内容を変えない文面の書き換えはカードにせず，任せた選択にする．
    - 文面への操作として問うと，ユーザーは対象の判断リストと照らし合わせないと判断できない．
- D44: 見直しは，候補を洗い出し，「ラウンド」の順位付けと出力に従って起票し，書くときに内容を変えない整えを行う，の3手順として1つの見出しの下に書く．候補は判断の内容が変わるものだけ（食い違い，消して任せた選択にしても成果物がおおむね同じになる判断，定義がなくても読み違えない語を定める判断，判断を支えていない理由）とし，判断と理由は書き直さず削除を推奨にする．
