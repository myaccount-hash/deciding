# presenting-decisions

## このスキルの目的
ルールに書いていない場面では，この目的に沿って判断する．

- ユーザーが本当に欲しいものを中心に，ユーザーの判断を確定させ，DECISIONS.mdに残す．
    - 判断には，実現すべき機能（要件）も実装レベルのものも含めてよい．どこまで含めるかは，その都度決める．
- DECISIONS.mdと実行環境から，その判断を満たす成果物を組み立てられるようにする．
    - 実行環境は，作業時点の既存コードベース，外部情報，AIの実行環境を指す．
    - 実行環境の内容は書き写さない．判断の中で実行環境に言及するのはかまわない．
    - 同一のコードではなく，判断を満たす成果物を目指す．
    - 記録にない選択は，AIが自由に判断したものとみなす．
- 記録に残るのは，ユーザーが見て決めた判断だけ．
    - 理解するかどうかは，ユーザーに任せる．AIは，理由・代替・質問への答えのように，理解するための材料を出す．
    - ユーザーは，理解するまで質問を重ねてよい．
- 判断負荷を下げる．
    - 下げるのは，1つの判断にかかる手間に限る．判断の数を減らしたり，判断をAIに任せたりはしない．
- ユーザーは，まとまっていない考えのまま投げてよい．
    - AIはそれを判断事項（推奨・理由・代替）に整え，「こういうことか」と返す．ユーザーはそれを見て確定させる．
- カードごとに議論を並列で進める．
    - 1枚のカードの議論は，他のカードが`OK`になるのを待たずに，ラウンドごとに進める．
- AIはユーザーの指示に従うだけの役ではなく，議論の相手として，自分の推奨と反論を出す．
    - 決めるのはユーザー，論じるのはユーザーとAIの両方．

## カード
- AIは判断事項を1枚ずつカードとして出す．ユーザーは各カードに，`OK`・`SKIP`・コメントのどれかで返答する．
- 「判断事項」は中身を，「カード」はAIが出す1件を指す．DECISIONS.mdに記録するのは判断で，カードではない．
- ラウンド: AIがカードを出してから，ユーザーが返答するまで．
- ラウンドループ: すべてのカードが`OK`になるか，ユーザーが`RUN`を指示するまで，ラウンドを繰り返すこと．

## 指示
- `DEAL`: 判断事項をカードとして出し，ラウンドループを始める．
- `SAVE`: DECISIONS.mdに記録する．
- `COMPACT`: DECISIONS.mdを圧縮する．
- `RUN`: `OK`の事項に従って成果物を作る．
- 英大文字の語は，それだけで書かれたときに限って指示とみなす．「記録して」のように明示的に頼む文も，同じ指示として受ける．
    - 理由: 「テストをrunする」のようなふつうの文で，誤って成果物を作りはじめないため．
- これらの指示がなければ，判断が必要な場面でも自発的に使わない．

## DECISIONS.md
- 既定の置き場所は作業フォルダのルート．ユーザーが置き場所を指定したら，それに従う．
- ファイルがなければ記録の時点で作成する．記録しないなら，ファイルなしで動く．
- ファイルがあれば，カードを出す前に読む．否定の印が付いた判断は無効とする．
- 記録と実行環境の食い違いや，記録した判断どうしの食い違いに気づいたら，常にその時点で判断事項として出す．外部の変化を前もって追う仕組みは設けない．

## 判断事項
- ユーザーに見せる情報は，カードでも記録でも，すべて判断事項にする．前提の欄は設けない．
    - 理由: 前提の欄は，ユーザーが確認しないまま記録に残る経路になる．
- 外部の制約（既存コード，連携先など）は判断事項にしない．AIが実行環境から読み取る．制約への対応をユーザーが選ぶ場合だけ，判断事項にする．
- AIからユーザーへの質問も，カードとして出してよい．
    - 問いには質問を書き，推奨にはAIの解釈や仮の答えを書く．
    - 当てがなければ，推奨に「当てがない」と書き，代替に考えられる答えの候補を並べる．
- 判断事項は，1つで1つのことだけを問う．複数のことを問うときは，分ける．
    - 推奨の中に，片方だけに賛成・反対できる部分が2つ以上あれば，1枚に複数のことが入っているとみなして分ける．
- 依存する下位の事項は，上位と同時に出す．
    - 上位が，同時に出したときの推奨と違う内容で`OK`になったら，下位を作り直して出し直す．下位に出ていた`OK`は無効にする．
- 記録した判断を否定・変更する事項では，変更後の判断そのもの（本文と理由）を推奨に書き，DECISIONS.mdを見なくても判断できる形にする．
    - 「〜の文を削るか」のような，記録の文面への操作としては問わない．
    - 対象の元のIDは，内容を1行添えて問いに書く．元の判断から意味がどう変わるかは，理由に書く．
    - 食い違いを出す場合も含める．圧縮で出す事項は，`references/compression.md`に従う．

## カードの書き方
- カードには，`#1`，`#2`のような番号を，ラウンドごとに1から振り直して付ける．
    - この番号は，返答でカードを指すためだけに使う．依存関係や，同じラウンドの他のカードを指すときも，この番号を使う．
    - ラウンドをまたいで同じカードかどうかは扱わない．
- 決まった欄（問い・推奨・理由・代替）だけをラベル付きで書く．問いは見出しに書く．それ以外の補いは，ラベルなしの箇条書きで自由に書ける．
- ラベル付きの欄は，内容が1つならラベルと同じ行に書き，複数あるならラベルの下に入れ子の箇条書きで並べる．入れ子の項目はその欄の一部で，`OK`は入れ子の項目にも及ぶ．
- 長さの目安は，推奨は3文まで，理由は3項目まで．
    - 超えそうなときは，まず分けられないかを確かめる．それでも超える場合は，そのまま出してよい．
    - 理由: 上限を絶対にすると，分けられない判断の理由が`OK`されないまま削られる．数字に根拠はなく，目安にとどめる．
- 記録した判断を指すときは，IDに内容を1行添える．まだ記録していない`OK`の事項は，内容で指す．

```
## #1: <問い>
- 推奨: ...
- 理由:
    - ...
    - ...
- 代替: ...
```

## ラウンドの出力
- 通常のテキストで出力する．選択肢UIは使わない．
- `OPEN`のカードは，毎ラウンド，推奨・理由・代替を付けてすべて出す．前のラウンドから変わっていないカードも省かない．
- 1ラウンドに出すカードの枚数に上限を設けない．
    - 理由: 上限を設けても判断の数は減らず，後回しになるだけ．
- カードの外には，今回`OK`になった事項の一覧と，返答のお願いのような進行のための文だけを書く．
    - 一覧には，コメントの解釈を確かめられるよう，`OK`になった内容を1行ずつ書く．
- 質問への答えや説明は，関係するカードの理由か，ラベルなしの箇条書きに書く．関係するカードがなければ，新しいカードにする．
- すべてのカードが`OK`になったら，一覧を出して止まる．記録していない`OK`の事項があれば，一覧の最後に「未記録」と1行添える．ユーザーの指示があるまで作業に進まない．

```
## 今回OKになった事項
- ...

## #1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 返答の処理
- ユーザーは，カードの番号を添えて返答する．番号のない`OK`や`SKIP`だけの返答は，そのラウンドのすべてのカードへの返答とみなす．

```
#1 OK
#2 SKIP
#3 〜のほうがよいのでは
```

- 返答は`OK`・`SKIP`・コメントの3つだけ．
    - `OK`: 推奨で確定する．`OK`は，カードに書いた推奨と理由の両方に及ぶ．
    - `SKIP`: そのラウンドでは判断しない．カードは`OPEN`のまま，次のラウンドでもう一度出す．返答のないカードも`SKIP`と同じに扱う．
    - それ以外の返答は，`NG`や「いいよ」も含めて，すべてコメントとして扱う．
- コメントを受けたら，修正の指示でも新しい提案でも，AIが独立に推奨を作り直す．
    - コメントの内容は，推奨に採っても，代替に載せても，どちらにもしなくてもよい．採らないときは，なぜ採らないかを理由に書く．
    - どのカードにもない事項を持ち込むコメントは，新しいカードにする．
- ユーザーの提案も判断事項にし，ユーザーが`OK`して確定とする．AIの同意だけでは確定しない．
    - 理由: AIの同意で確定すると，ユーザーが見ていない判断が`OK`の事項に混ざる．

## 状態
- 状態は`OK`と`OPEN`の2つだけ．`OPEN`はまだ`OK`されていない状態で，`SKIP`したカードや，コメントを受けて出し直したカードもこれに入る．
- `SAVE`で記録するのは`OK`の事項だけ．`OPEN`の事項は記録せず，AIの自由な判断に任される．
- `OPEN`の事項は，セッションをまたいで残らない．思いついただけのアイデアも，`OK`になるまでは記録に残らない．

## RUN
- `OK`の事項だけに従って成果物を作る．`OPEN`の事項が残っていても確かめずに進み，それらはAIの自由な判断に任せる．
- 記録していない`OK`の事項があれば，先に記録してから成果物を作る．
- このスキルを使っていること，DECISIONS.mdがあること，判断がどう出されどう決まったかは，成果物に持ち込まない．成果物は，それだけを読んで意味が通るように書き，判断の中身だけを反映する．
    - 持ち込まないもの: DECISIONS.mdやIDへの参照，スキル名，「合意に基づき」「ユーザーの判断で」のような，決まった経緯を示す書き方．
    - 成果物は，作業の結果として残るものすべて．コード，コードのコメント，ドキュメント，コミットメッセージ，PRの説明が該当する．DECISIONS.mdそのものと，セッション中の会話は含めない．
    - 判断の理由を成果物に残したいときは，理由そのものを，成果物の中だけで意味が通る文で書く．書くかどうか，どう書くかは，ふつうのコメントの書き方として判断する．
    - このスキルや，DECISIONS.mdを扱うツールを作る作業では，スキルやDECISIONS.mdについて書いてよい．その場合でも，IDや「〜で決めた」のような経緯は持ち込まない．
    - 理由: DECISIONS.mdは公開されるとは限らず，標準的な仕組みでもないので，読み手には通じない．圧縮でIDが振り直されるので，参照は不正確にもなる．

## 記録と圧縮
- `SAVE`を受けたとき，または`RUN`の前に記録していない`OK`の事項があるときは，`references/recording.md`を読んでから記録する．
- `COMPACT`を受けたときだけ，`references/compression.md`を読んでから圧縮する．

## 否定の印
DECISIONS.mdの既存の記録は書き換えず，否定された判断の下に次の印を1行追記する．

```
- D5: 設定ファイルはYAMLで書く．
    - 理由: ...
    - → D12で否定（2026-11-10 14:30 +09:00）
```
