# presenting-decisions

## このスキルの目的
ルールに書いていない場面では，この目的に沿って判断する．

- ユーザーが本当に欲しいものを中心に，ユーザーの判断を確定させ，DECISIONS.mdに残す．
    - 判断には，実現すべき機能（要件）も実装レベルのものも含めてよい．どこまで含めるかは，その都度決める．
- DECISIONS.mdと実行環境から，その判断を満たす成果物を組み立てられるようにする．
    - 実行環境は，作業時点の既存コードベース，外部情報，AIの実行環境を指す．
    - 実行環境の内容は書き写さない．判断の中で実行環境に言及するのはかまわない．
    - 同一のコードではなく，判断を満たす成果物を目指す．
- 記録に残るのは，ユーザーが見て決めた判断だけ．
    - 理解するかどうかは，ユーザーに任せる．AIは，理由・代替・質問への答えのように，理解するための材料を出す．
    - 記録にない選択は，AIが自由に判断したものとみなす．
- ユーザーの判断負荷を下げる．
    - 下げるのは，1つの判断にかかる手間に限る．判断の数を減らしたり，判断をAIに任せたりはしない．
- ユーザーは，まとまっていない考えのまま投げてよい．
    - AIはそれを判断事項に整え，「こういうことか」と返す．ユーザーはそれを見て確定させる．
- まだ決まっていないことを保持する．
    - 保持には，保留と未確定を使う．どちらも推奨・理由・代替を付けて記録し，次のセッションで提示する．
    - 思いついただけのアイデアも，判断事項の形にしてから保持する．

## 起動条件
- ユーザーが「判断事項を提示」などと明示的に指示したときだけ使う．
- 判断が必要な場面でも，指示がなければ自発的に使わない．

## DECISIONS.mdの置き場所
- 既定は，作業対象のリポジトリまたはフォルダのルート．
- ユーザーが置き場所を指定したら，それに従う．
- ファイルがなければ，記録の時点で作成する．記録しないなら，ファイルなしで動く．

## 既存の合意の参照
- DECISIONS.mdがあれば，判断事項を挙げる前に読む．
- 否定の印が付いた判断は無効とする．印の形は「記録の印」を参照．
- 未解決の保留と未確定の事項は，最初のラウンドで提示する．
    - 解決の印も更新の印もない保留が，未解決の保留．
- 記録と実行環境の食い違い，記録した判断どうしの食い違いに気づいたら，常にその時点で判断事項として提示する．
    - 外部の変化を前もって追う仕組みは設けない．

## 判断事項
- ユーザーに見せる情報は，すべて判断事項にする．前提の欄は設けない．
    - 理由: 前提の欄は，ユーザーが確認しないまま記録に残る経路になる．
    - 要件（目的，対象範囲など）も判断事項にする．
- 実行環境から読み取れることは，判断事項にしない．
    - 既存コード，連携先などの外部の制約は，AIが実行環境から読み取る．
    - 制約への対応をユーザーが選ぶ場合だけ，判断事項にする．
- AIからユーザーへの質問も，判断事項と同じ形で提示してよい．
    - 問いには質問を，推奨にはAIの解釈や仮の答えを書く．
    - 当てがなければ，推奨に「当てがない」と書き，代替に答えの候補を並べる．
- 判断事項は，1つで1つのことだけを問う．複数のことを問うときは，分ける．
- 他の事項が依存するもの，影響が大きいものを先に並べる．
- 事項間に依存関係があれば明記する．
    - 依存する事項も同時に提示する．
    - 上位の事項が推奨以外で確定したら，下位の事項を同じIDで作り直して再提示する．下位に出ていた了承は無効にする．

## 状態
- 確定: ユーザーが合意した．
- 未確定: ユーザーがまだ指示していない．
- 保留: ユーザーが「保留」と指示した．
    - 保留は，ユーザーの明示的な指示でだけ付ける．AIが勝手に付けない．
- 不要: ユーザーが「不要」と指示した．ユーザーはその事項を判断しない．
- ユーザーができる返答は，「OK」「保留」「不要」「コメント」の4つ．

## 各事項の書き方
- `D1`，`D2`のような通し番号を振る．
    - DECISIONS.mdがあれば，ファイルにある最大番号の続きから振る．なければ`D1`から振る．
    - ラウンドをまたいで番号を変えない．
    - 新たに追加する事項には続きの番号を振る．
- 各事項に次の項目を書く．
    - 問い: 見出しに書く．
    - 推奨: 推奨案．
    - 理由: 推奨する理由．
    - 代替: 推奨案以外の案．
- 各欄は，内容が1つならラベルと同じ行に書き，複数あるならラベルの下に入れ子の箇条書きで並べる．記録の理由も同じ．
- ラベルは，上の決まった欄にだけ付ける．それ以外の補い（依存関係など）は，ラベルなしの箇条書きで書ける．
- 判断が特定の外部情報（ファイル，URL，資料）に依存するときは，必要に応じて参照先を書いてよい．理由の中でも，補足の箇条書きでもよい．
- 他の判断事項を参照するときは，IDに加えて参照先の内容を1行で併記する．
    - 例: 「D7（コメントのない事項は再提示する）に従い…」
- 記録済みの判断を否定・変更する事項（食い違いの提示など）は，変更後の判断そのもの（本文と理由）を推奨に書く．
    - DECISIONS.mdを見なくても判断できる形にする．「〜の文を削るか」のような，記録の文面への操作としては問わない．
    - 対象の元のIDは，内容を1行で併記して問いに書く．
    - 元の判断から意味がどう変わるかは，理由に書く．
    - 圧縮で提示する事項は，この項ではなく`references/compression.md`に従う．
- ユーザーの提案に基づく事項は，推奨をAIが独立に作る．
    - ユーザーの提案は，内容を変えずに代替に載せる．
    - AIの推奨が結果として提案と同じになる場合だけ，提案を推奨にする．
    - 理由: 推奨と代替が提案に引っ張られず，ユーザーが比べて決められる．

```
## D1: <問い>
- 推奨: ...
- 理由:
    - ...
    - ...
- 代替: ...
```

## 出力手段
- 通常のテキストで出力する．選択肢UIは使わない．
    - 理由: コメントを，長文でも自由に書けるようにするため．
- カードの外には，今回確定した事項の一覧と，返答のお願いのような進行のための文だけを書く．
- ユーザーは自由記述でコメントする．

## コメントの処理
- 「OK」などの了承は，推奨案で確定とする．
    - 了承は，提示した推奨と理由の両方に及ぶ．
- 提示した代替案の選択は，その案で確定とする．
- 「保留」は，その事項を保留にする．
- 「不要」は，その事項をAIの自由な判断に任せる．以降提示せず，記録もしない．
    - 「その案はやらない」は判断なので，「不要」ではなく，「やらない」案を選ぶコメントで確定する．
- 修正の指示は，修正した内容を推奨にして，同じIDで再提示する．
    - 一部分だけに合意するコメントも，同じように扱う．
    - ユーザーが了承して確定する．
- 新しい提案は，新しいIDの判断事項として提示する．
    - ユーザーが了承して確定する．
- ユーザーは，理解するまで質問を重ねてよい．
- 質問や異論には答え，必要なら修正した推奨案を同じIDで再提示する．
    - 答えや説明は，関係する判断事項の理由か，ラベルなしの箇条書きに書く．関係する事項がなければ，新しい判断事項にする．
- コメントのない事項は未確定のまま，次のラウンドで再提示する．
- AIの同意だけでは確定しない．
    - 理由: AIの同意で確定すると，ユーザーが見ていない判断が合意済みに混ざる．

## 2ラウンド目以降の出力
- そのラウンドで新たに確定した事項，保留，未確定事項を出力する．
    - 新たに確定した事項は，コメントの解釈を確認できるよう確定内容を1行で示す．
    - 保留は，毎ラウンド，他の事項と同じ形（推奨・理由・代替付き）で提示する．
- 確定済みの事項は再掲しない．

```
## 今回確定した事項
- D2: ...

## D1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 全事項確定後
- 確定事項と保留の全一覧を出力して止まる．
- DECISIONS.mdに記録していない合意があれば，一覧の最後に「未記録」と1行添える．
- ユーザーの指示があるまで作業に進まない．

## 実装の依頼
- 未確定の事項が残っていれば，進む前に，確定か保留か不要かを指示してもらう．
- 未記録の合意があれば，実装の前にDECISIONS.mdに記録する．
- 保留は，最後に提示した推奨で実装する．
- 未確定の事項は，実装の根拠にしない．
- AIが実装中に自由に判断したことは，記録しない．
- このスキルを使っていること，DECISIONS.mdがあること，判断がどう提示されどう決まったかは，成果物に持ち込まない．成果物は，それだけを読んで意味が通るように書き，判断の中身だけを反映する．
    - 持ち込まない例: DECISIONS.mdやIDへの参照，スキル名，「合意に基づき」「ユーザーの判断で」のような，決まった経緯を示す書き方．
    - 成果物は，作業の結果として残るものすべてを指す．コード，コメント，ドキュメント，コミットメッセージ，PRの説明が該当する．DECISIONS.mdそのものと，セッション中の会話は含めない．
    - 判断の理由を成果物に残したいときは，理由そのものを，成果物の中だけで意味が通る文で書く．
    - 成果物の題材がこのスキルやDECISIONS.mdそのものなら，それらについて書いてよい．その場合でも，IDや決まった経緯は持ち込まない．
    - 理由: DECISIONS.mdは公開されるとは限らず，標準的な仕組みでもないので，読み手には通じない．圧縮でIDが振り直されるので，参照は不正確にもなる．

## 記録と圧縮
- ユーザーが「記録」と指示したとき，または実装を依頼されて未記録の合意があるときは，`references/recording.md`を読んでから記録する．
- ユーザーが「圧縮」と指示したときだけ，`references/compression.md`を読んでから圧縮する．

## 記録の印
DECISIONS.mdの既存の記録は書き換えず，次の印を1行追記して状態を表す．

否定された判断:

```
- D5: 設定ファイルはYAMLで書く．
    - 理由: ...
    - → D12で否定（2026-11-10 14:30 +09:00）
```

解決された保留:

```
- D9（保留）: <問い>
    - 推奨: ...
    - 理由: ...
    - 代替: ...
    - → D13で解決（2026-11-10 14:30 +09:00）
```

推奨が変わった保留（新しい記録に同じIDで書き直されている）:

```
- D14（保留）: <問い>
    - 推奨: ...
    - 理由: ...
    - 代替: ...
    - → 2026-11-12 09:00 +09:00の記録で更新
```
