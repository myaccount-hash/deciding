# toolkit-smith

## 目的
toolkitの目的は，次回以降の作業で，消費するコンテキストを減らし，速度と正確性を上げること．規約にない場面では，この目的から判断する．

## 語
- toolkit: `<対象>-toolkit`という名前のスキル．対象の種類は縛らない(サービス，機器，データなど)．`<対象>`として名前を付けられる範囲を，1つのtoolkitとする．
- スクリプト: toolkitの`scripts/`に置く実行ファイル．
- レシピ: toolkitの`recipes/`に置く手順．
- ツール: スクリプトとレシピをまとめた呼び名．

## 手順
1. 置き場所を決める．既存のtoolkitはその場所で直す．新しいtoolkitの置き場所はユーザに聞く．
2. 追加・変更・削除するツールを決める．新しいtoolkitには，依頼された作業に必要なツールだけを入れる．
3. 書換える前に，追加・変更・削除するツールをユーザに見せ，承認を得る．
4. 書換える．

## 構成
```
<対象>-toolkit/
    SKILL.md
    scripts/<name>.py
    recipes/<name>.md
```

- toolkitはこのスキルに依存も言及もせず，単独で配布できる形にする．
- スクリプトもレシピも並列に置き，toolkitの中で担当範囲を重ねない．
- レシピは1つずつ別のファイルにする．
- ツールにもSKILL.mdにも，作業固有の情報(特定のリポジトリ，ID，人名など)を書かない．

## toolkitのSKILL.md
- descriptionには，対象の名前を必ず入れる．
- 本文には，ツール一覧と，自己修復・自己拡張のときの振舞いだけを書く．この規約は書かない．
- ツール一覧は1つにまとめ，1項目を1行で「`<ファイルのパス>`: <説明>」と書く．説明は全角30字以内で，使い方や実装ではなく，関心を書く(例: 「xxxを読む」)．
- 自己修復・自己拡張のときの振舞いは，次の3つを書く．
    - toolkit自身のファイルは書換えず，報告と提案だけをする．
    - 作業中に不整合を見つけたら，作業後にユーザに報告する．
    - 実行した後，拡張が必要と判断したらユーザに提案する．

```markdown
---
name: <対象>-toolkit
description: <対象>の...
---

# <対象>-toolkit

## ツール
- `scripts/<name>.py`: <関心>
- `recipes/<name>.md`: <関心>

## 修復と拡張
- このtoolkitのファイルは書換えず，報告と提案だけをする．
- 作業中に不整合を見つけたら，作業後にユーザに報告する．
- 実行した後，拡張が必要と判断したらユーザに提案する．
```

## スクリプト
- 単独で配布できる形にする．
- 仕様と使い方は，スクリプトの中に書く(Pythonならdocstring)．
- 間違えにくく，数行で書ける処理はスクリプトにしない．

## レシピ
- 「複数のスクリプトの組合せ」「AIによる出力の確認」「人間への確認」のどれかを含むものだけをレシピにする．スクリプト1つを実行するだけの手順はレシピにしない．
- 1つの見出しと番号付きの手順だけで書く．各手順には，実行するスクリプト，AIによる出力の確認，人間への確認のどれかを書く．
- 手順だけを書き，背景知識や外部ドキュメントの写しは書かない．
- 他のレシピに依存も言及もしない．

```markdown
# <関心>
1. `scripts/<name>.py`を実行する．
2. 出力に...が含まれることを確かめる．
3. ...でよいかをユーザに確かめる．
```
