# toolkit-smith
- D1: toolkit-smithスキルを新しく作る．今回は個々のtoolkitは作らない．
    - toolkitはsmithが作るので，まずsmithがあれば足りる．
    - 見本のtoolkitを同時に作ると，対象固有の判断が混ざって判断の数が増える．
- D2: smithに，toolkitの目的として「次回以降の作業で，消費するコンテキストを減らし，速度と正確性を上げる」と書く．
    - 規約に書いていない場面で，判断の拠り所になる．
- D3: smithには，最初の1つのtoolkitを作るのに必要な規約だけを書く．それ以外は，実際に使ってみて問題(読み違い，失敗，同じ手順の繰返し，担当範囲の重なり)が起きてから書き足す．
    - 使う前に予想で書いた規約は，予想が外れたときに直す手間がかかる．
    - SKILL.mdが短いほど，読込むコンテキストが減る．
- D4: スクリプトとレシピを合わせて「ツール」と呼び，smithの中で定義する．
    - smithの規約では両方をまとめて指す場面が多く，呼び名があると文が短くなる．
- D5: 呼び名は「スクリプト」と「レシピ」にする．
    - workflowやplaybookは，GitHub ActionsやAnsibleの用語とぶつかる．
    - レシピは「材料(スクリプト)を組み合わせる手順」という意味が伝わる．
- D6: toolkitの名前は`<対象>-toolkit`とする．
    - 対象の名前が先頭にくるので，スキル一覧で探しやすく，descriptionとの照合でも見つかりやすい．
- D7: toolkitの対象の種類は縛らない．サービスでも，機器でも，データでもよい．`<対象>-toolkit`の<対象>として名前を付けられる範囲を，1つのtoolkitとする．
    - 「MacBookの情報を集める」のような，サービスではない対象も扱える．
    - 名前の形(D6)が，範囲の切り方の制約を兼ねる．
- D8: toolkitの規約はsmithの中だけに置く．各toolkitのSKILL.mdには，一覧と，自己修復・自己拡張のときの振舞いだけを書く．
    - 規約を各toolkitに写すと重複し，toolkitごとに内容がずれていく．
    - toolkitを使うときに規約は要らないので，読込むコンテキストが減る．
- D9: toolkitはsmithに依存も言及もせず，単独で配布できる形にする．
    - smithがない環境に配っても，toolkitはそのまま使える．
- D10: toolkitは，toolkit自身のファイルを書換えず，報告と提案だけをする．書換えるのは，ユーザの指示を受けたsmithだけにする．
    - 作業中に書換えると，作業の結果とtoolkitの変更が混ざり，ユーザが変更を確かめにくい．
    - 規約を知っているのがsmithだけで済む(D8)．
- D11: smithのdescriptionには「名前が`-toolkit`で終わるスキルを作る・直す・拡張するときに使う」と書く．
    - toolkitの報告には必ずtoolkitの名前が出るので，続けて「修正して」と言えば，`-toolkit`という語でsmithが選ばれる．
    - toolkitの側に何も書かなくても，smithに呼出しがつながる(D9)．
- D12: toolkitのdescriptionには，対象の名前を必ず入れる，とだけ決める．
    - 対象の名前があれば，作業の依頼からtoolkitが選ばれる．
- D13: smithは置き場所を決めない．既存のtoolkitはその場所で直し，新しいtoolkitの置き場所はユーザに聞く．
    - claude.aiとClaude Codeでは，スキルの保存のしかたが違う．
    - 最初の1つのtoolkitから，どこかに書く必要がある．
- D14: smithは書換える前に，追加・変更・削除するツールをユーザに見せ，承認を得る．
    - 「追加は定められた手順で行う」を満たす，最小限の手順になる．
- D15: smithが作るtoolkitには，依頼された作業に必要なツールだけを入れて始める．
    - 使われないツールは，一覧を長くするだけになる．
    - 足りないツールは，自己拡張の提案で後から足せる．
- D16: 「ツールにもSKILL.mdにも，作業固有の情報(特定のリポジトリ，ID，人名など)を書かない」と書く．
    - 書込まれていると，次の作業でAIがそれを前提として読んでしまう．
- D17: 認証情報や環境ごとの値についての規約は書かない．
- D18: 「スクリプトもレシピも並列に置き，toolkitの中で担当範囲を重ねない」と書く．
    - 重なっていると，片方だけが直されて食い違う．
- D19: レシピは1つずつ別のファイルにする．
    - SKILL.mdを読込んだ時点のコンテキストが，一覧の分だけで済む．
    - 追加と削除がファイル単位になるので，並列に管理できる．
    - 構成の例:

        ```
        <対象>-toolkit/
            SKILL.md
            scripts/<name>.py
            recipes/<name>.md
        ```

- D20: SKILL.mdのツール一覧は1つにまとめ，各項目を「`<ファイルのパス>`: <説明>」と書く．
    - AIは一覧からそのままファイルを開け，名前とファイルの対応を別に覚えなくてよい．
    - 種類はパスでわかるので，スクリプトとレシピで一覧を分けなくてよい．
- D21: 一覧は1項目を1行とし，説明は全角30字以内にする．一覧全体の上限は設けない．
    - 項目ごとに上限があれば，説明に機能まで書込むのを防げる．
    - 一覧全体の長さは，実際に問題になってから決めればよい(D3)．
- D22: 一覧の説明については，「使い方や実装ではなく，関心を書く(例: 「xxxを読む」)」とだけ書く．
    - ユーザの言葉と例で，意味は十分に伝わる．
- D23: 自己修復については，「作業中に不整合を見つけたら，作業後にユーザに報告する」とだけ書く．報告に書く項目や，作業中の振舞いは決めない．
- D24: 自己拡張については，「実行した後，拡張が必要と判断したらユーザに提案する」とだけ書く．判断の基準は決めない．
- D25: スクリプトは単独で配布できる形にする．
    - toolkit専用にすると，そのスクリプトをtoolkitの外で使い回せなくなる．
- D26: 「間違えにくく，数行で書ける処理はスクリプトにしない」とする．
    - これより細かい基準は予想に基づく規約で，D3と食い違う．
- D27: スクリプトの言語は縛らない．
    - 言語を縛るのは予想に基づく規約で，D3に合わない．
- D28: スクリプトの仕様と使い方は，スクリプトの中に書く(Pythonならdocstring)．
- D29: スクリプトに`--help`は求めない．
- D30: レシピにするのは，「複数のスクリプトの組合せ」「AIによる出力の確認」「人間への確認」のどれかを含むものだけ．スクリプト1つを実行するだけの手順はレシピにしない．
    - スクリプト1つで済む手順は，スクリプトの中の仕様に書いてあれば足りる．
- D31: レシピについては，「手順だけを書き，背景知識や外部ドキュメントの写しは書かない」と書く．
    - 「膨大な文書をレシピに載せたいわけではない」というのは，前もってはっきり示された要件．
- D32: 「レシピは他のレシピに依存も言及もしない」と書く．
    - あるレシピを消したり変えたりしても，ほかのレシピが壊れない．
- D33: レシピは，1つの見出しと番号付きの手順だけで書く．各手順には，実行するスクリプト，AIによる出力の確認，人間への確認のどれかを書く．
    - レシピに含めるのはこの3つ(D30)なので，どの手順もこの3つのどれかで書き表せる．
    - 手順以外を書かないこと(D31)を，形のうえで守れる．
